## 一、[`F-12`] Claude 5h / 7d 额度显示方案（GitHub 开源选型思路）

### 1.1 目标与核心矛盾
- **用户想看什么**：在桌面端/控制台直观看到当前账号的 **5 小时滚动窗口用量（5h）** 与 **7 天周限额（7d）**，避免高强度开发时突然撞墙 429。
- **核心矛盾**：Anthropic 对 Pro/Max 订阅没有正式公开的只读额度 REST API；所有开源方案都在 **「数据准确度」×「账号封控/隐私风险」×「适用覆盖面（桌面端 vs CLI vs Web）」** 三角里做妥协。

### 1.2 三条主流技术路线对等对比

| 路线 | 代表思路 / 开源参考 | 优点 | 缺点 / 隐性代价 / 真实坑点（必看） | 综合评估 |
| :--- | :--- | :--- | :--- | :---: |
| **路线 A：复用已内置 `sessionKey` 查 Web 内部接口** | 在用户已手动粘贴 `sk` 做云端审计时，顺带探测 `/api/organizations/{org}/usage`（或同源计费接口） | 1. **零新增敏感凭据**（复用现有内存 `sk` 走代理通道，绝不读磁盘明文 OAuth）；<br>2. 覆盖 Web + Desktop + CLI 全端合并真实用量；<br>3. 准确度最高 | 1. **强依赖 `sk` 有效期**（过期需重新粘贴，无法做到全自动后台每 5 分钟刷新）；<br>2. 非官方稳定契约，Anthropic 随时可能改字段或加 CF 盾；<br>3. 高频轮询会直接触发 429 / 风控，**绝不能后台自动定时轮询**，只能手动按需点查 | **最契合本工具安全红线（推荐优先验证）** |
| **路线 B：纯离线解析本机 CLI JSONL 日志（`ccusage` 思路）** | 解析 `~/.claude/projects/**/*.jsonl` 中的 `usage` token 统计，按本地时间窗口估算 5h / 7d 消耗 | 1. **100% 离线、零联网、零封号风险、零凭据泄露风险**；<br>2. 无需 `sk`，随时秒算，可实时刷新 | 1. **只能算本机 Claude Code CLI 用量**，完全看不到 Claude Desktop 桌面端、网页端和手机端消耗；<br>2. 官方 5h/7d 限额是动态加权权重（随模型/缓存/时段浮动），离线只能算「Token 数量 / 估算成本」，**无法算出精确百分比剩余额度**，容易让用户以为“算不准” | **适合作为无 `sk` 时的“本机 CLI Token 消耗参考”互补项** |
| **路线 C：读取本机 OAuth Token 调 `/api/oauth/usage`** | 读取 `~/.claude/.credentials.json` 或系统凭据库里的 OAuth Token 直调 Anthropic 接口 | 无需用户粘贴 `sk`，可自动刷新精准百分比 | **踩中严重隐私与封号红线**：<br>1. 读取用户明文 OAuth 凭据并在第三方工具里复用，极其容易被开源社区质疑为窃取 Token；<br>2. 曾多次出现非官方客户端高频调用 `/api/oauth/usage` 触发 429 甚至异常风控告警；<br>3. 与本工具「不碰、不转存用户 OAuth 凭据」的安全承诺直接冲突 | **明确否决（不建议采用）** |

### 1.3 建议落地思路（待后续验证）
- **双轨互补、诚实标注**：
  1. **主轨（路线 A）**：在「有 `sk` 手动云端核验」时顺带试探官方 usage 端点，拿得到就精准展示 `5h / 7d` 真实百分比并标明采集时间（不后台轮询）；
  2. **辅轨（路线 B）**：无需 `sk` 即可在本地离线统计本机 Claude Code CLI 过去 `5h / 7d` 的真实 Token 消耗与模型分布（明确标注「仅本机 CLI 统计，不含网页/桌面端」）。

## 二、[`F-15`] AI 检验工具自身安全性（开源安全审计思路 · 对应 Q7）

### 2.1 背景与核心价值
- 本工具涉及**管理员提权、修改 Clash 脚本、读写防火墙规则、以及用户粘贴 `sessionKey`**，天然是高敏感安全软件。用户（尤其是开源社区）最担心的 3 件事是：
  1. 有没有偷偷外传 `sk` / 邮箱 / 聊天记录？
  2. 提权后到底动了 Windows 哪些注册表、网卡和文件？
  3. 卸载或出问题时能不能 100% 干净还原？

### 2.2 备选形态对比（对应 Q7）

| 形态 | 内容与做法 | 优点 | 缺点 / 代价 |
| :--- | :--- | :--- | :--- |
| **A. 仓库级开源安全审计报告（`SECURITY-AUDIT.md` + 自动化门禁）** | 输出一份可由第三方复现的安全白皮书：列出全部外连域名白名单、全部系统写操作清单与对应撤回点、`sk` 内存零落盘证明、第三方依赖 `cargo audit` / `npm audit` 结果、以及 `check:contracts` 静态防泄密门禁说明 | 面向 GitHub 开源用户和审阅者最直接、可信度高、可随发版在 CI 中持续更新，不增客户端体积 | 终端普通下载用户不一定去翻 GitHub 文档 |
| **B. 客户端内「安全透明自检面板」** | 在「系统设置 → 关于/安全透明」中展示只读清单：当前外连端点列表、本工具历史写操作审计日志、一键自检 `sk` 零落盘验证结果 | 普通用户在软件内直接可见，安全感强 | 本工具「系统设置 → 清理恢复」已展示全部系统改动，「日志工具」已可导出透明诊断包，再叠一层面板有轻微信息重复与维护成本 |
| **C. 双轨（先 A 后 B 轻量入口 · 推荐）** | **优先落地 A**（仓库内独立 `SECURITY-AUDIT.md` + 接入 `cargo audit` / 外连域名自动静态扫描进 `check:contracts`），同时在「系统设置 → 版本更新/关于」底部加 1 行直达 GitHub 安全审计文档的轻量链接 | 投入产出比最高，真正把“安全审计”变成**每个版本自动跑的工程门禁**而非一次性公关文档 | 需要维护静态域名白名单，后续每新增一个外连接口都要同步登记 |

## 三、[`F-18`] 「AI 工具箱」首批真实功能规划思路

### 3.1 现状与定位红线
- 当前 [AiToolsPage.tsx](file:///c:/Users/xujun/Documents/ProgramProject/FDtools/src/pages/AiToolsPage.tsx) 为克制留白占位页，但占据了 4 个顶层一级导航之一；
- **定位红线**：不能做成大杂烩（偏离主业），只做**面向 Claude Desktop / Claude Code 日常高频痛点、本地只读/可逆、且不越权不碰账号认证**的轻量实用小工具。

### 3.2 首批 3 个高价值候选模块对比

| 候选模块 | 解决的真实痛点 | 优点 | 缺点 / 坑点 | 推荐优先级 |
| :--- | :--- | :--- | :--- | :---: |
| **1. MCP 服务器配置体检与开关管理器** | 用户手改 `claude_desktop_config.json` 与 `~/.claude.json` 经常写错 JSON 语法、路径缺转义、或想临时停用某个占内存的 MCP 却要手动删代码 | **极高频刚需**；100% 本地 JSON 读写（复用现有原子写 + 备份机制）；可视化的「启用/暂禁」开关 + JSON 校验 + 一键备份还原 | 不同 MCP 写法差异较大（`stdio` / `sse` / `http`、`env` 敏感 Key 需默认打码脱敏展示），暂禁状态需独立存旁路缓存避免破坏官方 Schema | **首选 #1** |
| **2. 本机 Claude Code Token / 会话统计与归档导出** | 想回看自己最近 5h/7d 在哪些项目里烧了多少 Token，或把某个历史会话导出为干净的 Markdown 归档 | 与 `F-12` 路线 B 天然融合，100% 离线只读，安全零风险，开发者好感度极高 | 若用户只用 Claude Desktop 网页壳不用 CLI，该模块数据为空（需做好空态提示） | **首选 #2** |
| **3. `CLAUDE.md` / 全局指令与项目规范快检器** | 多个项目散落 `CLAUDE.md` 与全局 `~/.claude/CLAUDE.md`，切换项目时常忘自己配了什么规则 | 实现简单、纯文件只读浏览与快速打开目录 | 强偏向重度 CLI 开发者，普通桌面端聊天用户感知较弱 | 备选 #3 |

## 四、[`F-17`] 开源版本广告位 / 赞助位设计思路（对应 Q9）

### 4.1 现状与审慎边界
- 工作区已有探索原型 [ui-v3-aitools-promo-preview.html](file:///c:/Users/xujun/Documents/ProgramProject/FDtools/docs/mockups/ui-v3-aitools-promo-preview.html)（5 种克制互动卡片风格）；
- **核心风险与短板（必须直视）**：
  1. **信任折损风险**：本工具主打“极简、克制、防封安全工具”，一旦在「控制台」「账户审计」「节点流量」等高频安全主战区插广告，或出现花哨动效/弹窗，极易引发开源用户反感并被质疑“带货推广高危中转/野鸡机场”；
  2. **合规与连坐风险**：若推广第三方中转站/拼车号/共享机场，而该赞助商恰恰踩了本工具自己宣传的防封红线，会瞬间摧毁产品公信力。

### 4.2 克制落地思路建议（待 Q9 拍板）
1. **排期节奏建议**：**先等核心功能（`01~03` 批）完全稳定、社区口碑建立后再启用**；当前阶段可先保留「开发者赞助/支持开源」机制；
2. **推荐投放位置（按打扰度从低到高）**：
   - **首选位置**：「AI 工具箱」底部/独立生态推荐区（功能补齐后顺带放 1~2 张克制静态卡片，明确标注 `赞助商 / 社区推荐`，不喧宾夺主）；
   - **次选位置**：「系统设置 → 版本更新 / 联系作者」底部的致谢赞助栏；
   - **严禁位置**：控制台、账户审计、节点流量主工作区、HUD 悬浮窗、系统弹窗（任何安全核心路径 0 广告）。
3. **技术原则**：采用**纯本地静态配置或极低频只读 JSON 拉取（失败静默隐藏、绝不阻断启动、0 追踪脚本、0 第三方 Cookie/埋点）**，并提供明确的“不追踪隐私”声明。

## 五、[`F-19`] Windows Authenticode 代码签名证书路径对比（远期规划）

### 5.1 痛点
- 未签名的 NSIS 安装包在 Windows SmartScreen 下会弹出“Windows 已保护你的电脑”拦截蓝窗，极大抬高普通用户安装门槛。

### 5.2 三条可行路径对等对比

| 路径 | 费用与门槛 | 优点 | 缺点 / 坑点 |
| :--- | :--- | :--- | :--- |
| **1. SignPath.io 开源免费签名计划** | 免费（需严格满足开源合规审查） | 0 证书费，直接依托 GitHub Actions 自动签名 | 1. 审批周期较长且要求全链路开源构建可复现；<br>2. **若软件包含闭源商业版/广告商业化或反代/代理工具类敏感属性，存在审批被拒风险** |
| **2. Microsoft Azure Trusted Signing** | 约 \$9.99 / 月起 | 按月付费无高额年费、支持 CI 自动化、SmartScreen 信誉积累快 | 1. 个人开发者认证目前受地区/企业主体限制（中国大陆主体通常无法直接开通个人/企业身份验证）；<br>2. 需海外合规实体或个人资质 |
| **3. 传统 OV / EV 代码签名证书** | OV 约 \$200~400/年；EV 约 \$400~700/年 | 主体清晰可控，EV 可快速过 SmartScreen 蓝窗 | 1. **成本高**；<br>2. 新规要求私钥必须存放在硬件 USB Token 或云 HSM 中，接入 GitHub Actions 自动化繁琐；<br>3. OV 初期仍需积累下载信誉才能消除蓝窗 |

- **阶段性结论**：在用户规模与主体资质尚未匹配前，保持 `F-19` 为远期规划；短期通过 GitHub Releases 公开发布 **SHA-256 校验值 + 开源构建日志 + 一句话 SmartScreen 放行说明** 降低用户顾虑。
